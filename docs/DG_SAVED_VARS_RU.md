# Переменные, сохраняемые в предмете

Как записать в предмет свои данные из триггера так, чтобы они пережили перезагрузку мада.
Механизм для иммов и билдеров, в игровой справке его нет и быть не должно.

Добавлен в январе 2024 (issue #2130). Код: `src/engine/scripting/dg_scripts.cpp`, поля
объекта `SavedInfo`, `savevar`, `loadvar`; сохранение — `src/engine/db/obj_save.cpp`.

---

## Три поля

```
%obj.savevar(имя)%     записать в предмет переменную с таким именем
%obj.loadvar(имя)%     достать её обратно в переменную триггера
%obj.SavedInfo%        вся строка хранилища целиком: читать и писать сырьём
```

`savevar` не принимает значение — он принимает **имя уже существующей переменной** и ищет её
в трёх местах подряд: сперва среди переменных самого триггера, потом среди глобальных
переменных скрипта (с учётом `context`), потом среди мировых. Не нашёл — пишет в лог
«Не найдена переменная X» и ничего не делает.

`loadvar` кладёт найденное в переменную триггера с тем же именем и контекстом 0. Если
в предмете ничего не сохранено, в лог уйдёт «Нет сохраненных переменных».

## Пример

```
* запомнить на предмете, кто его выковал и когда
set smith %actor.name%
set forged %date.unix%
%self.savevar(smith)%
%self.savevar(forged)%

* ... спустя перезагрузку, в другом триггере ...
%self.loadvar(smith)%
%self.loadvar(forged)%
if %smith% == %actor.name%
  osend %actor% Клинок узнал руку хозяина.
end
```

## Как это лежит внутри

Всё хранится одной строкой в поле `dgscript_field`, пары разделены решёткой:

```
smith Стрибог#forged 1794648232#
```

Имя — **первое слово** до пробела, значение — всё остальное до `#`. Отсюда два запрета:

- **`#` в значении недопустим** — это разделитель, строка развалится;
- **пробел в имени недопустим** — всё после первого пробела считается значением.

Длина всей строки ограничена `kMaxInputLength` — **2048 знаков**. При переполнении триггер
пишет «Список переменных переполнен, сократите на N символов» и запись **не делается**.

Посмотреть, что лежит в предмете, можно богом: `stat <предмет>`, строка «Сохраненные
переменные из DGScript».

## Что переживает перезагрузку, а что нет

Сохраняется не предмет сам по себе, а предмет **в сейве игрока**. Строка пишется как
`DGsc: ...~` в файле вещей (`obj_save.cpp`).

| где лежит предмет | переживёт ребут |
|---|---|
| в инвентаре игрока, надет | **да** |
| в ренте, в персональном хранилище, в клановом сундуке | **да** |
| лежит в комнате | нет |
| в контейнере, который лежит в комнате | нет |
| в инвентаре моба | нет |

Мир после перезагрузки собирается из прототипов заново, и всё, что лежало «в мире»,
исчезает вместе с записанным. Это не особенность `SavedInfo` — так со всеми предметами.

## Почему не `val0`..`val3`

Писать свои данные в игровые слоты (`%obj.val1(5)%`) можно, и у предмета в сейве игрока они
тоже сохранятся: `obj_save.cpp` пишет те значения, что отличаются от прототипа. Но при
загрузке вызывается `remove_incorrect_values_keys(тип)`, и он **выбрасывает ключи, не
подходящие типу предмета**: у зелий, сосудов и фонтанов оставляет только питейные, у свитков,
палочек и посохов — только заклинательные. То есть запись в чужой слот может пропасть, даже
лёжа в сейве.

`SavedInfo` такой проверки не знает и для своих данных надёжнее. Слоты `val` оставляем
игровой механике.

## У мобов такого нет

Полей `savevar`/`loadvar`/`SavedInfo` у мобов не существует, и сделать их «как у предметов»
нельзя: NPC нигде не сохраняются, после перезагрузки мир строится из прототипов. Хранить
нечего и негде.

При жизни моба переменные есть и так — обычные `global` и `remote` в его скрипте. Они живут,
пока жив моб, и умирают вместе с ним и с перезагрузкой.

Если нужно «запомнить на весь мир» — это мировая переменная (`worlds`), а не свойство моба.
